# Sarfkor — техническая документация

## 1. Что это за проект

**Основной продукт — B2B: система автоматизации магазина** для рынка Таджикистана. Прямой ориентир и конкурент — **myfin.tj**: касса (POS), складской учёт, закупки и поставщики, ценообразование, акции и лояльность, отчётность по продажам и прибыли. Платящий клиент — магазин; вся бизнес-модель строится вокруг партнёрского кабинета.

**Вторичный слой — B2C: приложение сравнения цен.** Пользователь сканирует штрихкод телефоном → видит цену в ближайших магазинах, историю цены, акции и альтернативы дешевле. Это **не отдельный продукт**, а (а) канал привлечения магазинов и (б) главное отличие от myfin.tj: подключённый магазин автоматически получает витрину для покупателей, чего у конкурента нет. Данные берутся из тех же `PriceEntry`, которые магазин и так ведёт в кабинете, плюс краудсорс от пользователей.

**Телефон — основное рабочее устройство магазина, а не аксессуар покупателя.** Камера телефона заменяет аппаратный сканер штрихкодов в двух ключевых сценариях магазина:
- **Приёмка на склад** — сотрудник наводит камеру на штрихкод, товар приходуется в остаток
- **Продажа на кассе** — кассир сканирует товары телефоном, позиции попадают в чек

Это осознанное продуктовое решение под рынок Таджикистана: магазину не нужно покупать POS-терминал и USB-сканер, достаточно телефона, который у него уже есть. Порог входа для магазина — ноль по железу. Аппаратные сканеры при этом должны продолжать работать (они эмулируют клавиатуру), но обязательным оборудованием не являются.

**Правило разрешения конфликтов:** если функция полезна покупателю, но мешает магазину (нагрузка, раскрытие коммерческих данных, усложнение кассы) — **побеждает магазин**.

**Команда:** 2 человека. Backend-разработчик — Мурод (.NET/C#, ASP.NET Core, EF Core, Clean Architecture, PostgreSQL/Npgsql).

**Стадия:** рабочий бэкенд и фронтенд против реальной PostgreSQL — 55 сущностей, ~100 эндпоинтов на MVC-контроллерах со Swagger, Identity+JWT, POS с проверенными инвариантами, 259 проходящих тестов, CI. Подробная хронология — в `WORKLOG.md`.

## 2. Обязательные технические требования (не обсуждаются)

- **Clean Architecture** строго: Domain / Application / Infrastructure / WebApi — без нарушения границ слоёв (Domain не знает про Infrastructure и т.д.)
- **SOLID** — обязательно в каждом классе/модуле:
  - SRP — один класс = одна причина для изменения
  - OCP — расширение через абстракции, не через правки существующего кода
  - LSP — наследники не ломают контракт базового типа
  - ISP — маленькие специфичные интерфейсы вместо one-size-fits-all
  - DIP — зависимости от абстракций (интерфейсов), не от конкретных реализаций; DI-контейнер ASP.NET Core
- **Безопасность — приоритет №1.** Проект работает с чеками, геолокацией, платёжными данными магазинов — потенциальная цель для атак. При любом решении сначала думать "как это может быть взломано"
- **Максимальная валидация везде**: обязательно дублировать валидацию фронта на бэке (никогда не доверять фронту) — DTO/Command через FluentValidation, плюс доменная валидация внутри Entity/Value Object
- **Финансовая транзакционность (модуль кассы)**: продажа + списание склада — только в одной DB-транзакции; все операции с деньгами и складом идемпотентны и полностью аудит-логируются

### Конкретные меры безопасности по умолчанию

- **Аутентификация/авторизация**: ASP.NET Identity + JWT, роли `User` / `StorePartner` / `Admin`, авторизация на уровне эндпоинтов (`[Authorize(Roles = "...")]`) И дополнительно на уровне use-case (не полагаться только на атрибут)
- **Input validation**: строгая валидация всех входных DTO (длина строк, форматы, диапазоны, санитизация) — FluentValidation в Application слое
- **SQL-инъекции**: только через EF Core с параметризованными запросами, никакого raw SQL с конкатенацией строк
- **XSS**: экранирование пользовательского контента (отзывы, названия товаров от юзеров) на выводе
- **CSRF**: antiforgery токены при cookie-сессиях; при JWT — строгая CORS-политика (белый список origin, не `AllowAnyOrigin`)
- **Rate limiting**: на эндпоинты сканирования, добавления отзывов, регистрации, `ProcessSaleCommand` — конкретные лимиты по каждому эндпоинту, не общая формулировка
- **Загрузка файлов** (фото товара, скрин чека): проверка типа файла по содержимому, ограничение размера, хранение вне веб-корня
- **Пароли**: хэширование через ASP.NET Identity (PBKDF2/Argon2), никогда plain text
- **Секреты**: connection strings, JWT-ключи — через переменные окружения / Secret Manager, никогда в репозитории
- **HTTPS everywhere**, HSTS в проде
- **Логирование без утечки чувствительных данных**: не логировать пароли, токены, платёжные данные
- **Платежи**: никогда не хранить полные данные карт на своей стороне — только токенизация через платёжного провайдера (PCI DSS scope — вне нашей ответственности)

## 3. Технический стек

- **Backend:** ASP.NET Core (.NET 10), Clean Architecture — Domain / Application / Infrastructure / WebApi
- **База данных:** PostgreSQL через Npgsql.EntityFrameworkCore
- **Валидация:** FluentValidation в Application слое (бэк — источник истины, фронт дублирует для UX)
- **Авторизация:** ASP.NET Identity + JWT, роли User / StorePartner / Admin
- **Frontend:** React + Vite + TypeScript + Tailwind; сканирование штрихкода — нативный `BarcodeDetector`, без сторонних библиотек
- **Целевое устройство магазина — телефон.** Кабинет, касса и склад должны быть пригодны для работы с телефона, а не только с десктопа (§1)

## 4. Модуль кассы/POS и склада — ключевая логика бэка

### Сканирование штрихкода — общий механизм для кассы и склада
- **Камера телефона — основной способ ввода штрихкода** (см. §1), аппаратный сканер и ручной ввод — равноправные альтернативы, но не обязательные
- Реализация — `BarcodeDetector` (Shape Detection API), поддерживается только в Chromium (Android/desktop); в Safari и Firefox, то есть на всех iPhone, камера недоступна — **ручной ввод обязан оставаться везде**, камера это быстрый путь, а не единственный
- `getUserMedia` работает только в secure context: **https или localhost**. Заход с телефона по локальному IP (`http://192.168.x.x`) камеру не запустит — в проде https обязателен, это не опция
- Логика сканера — единый переиспользуемый компонент на кассу, склад и потребительский экран, не три копии (SRP/DRY, §2)
- Касса сканирует **непрерывно** (кассир пробивает товары подряд, окно не закрывается на каждый товар) с дедупликацией: один и тот же штрихкод в пределах ~1.5 сек не должен создавать вторую позицию. Склад — одиночное распознавание
- Обязательная обработка: отказ в доступе к камере, отсутствие камеры, небезопасный контекст — понятным текстом, не пустым чёрным прямоугольником

### Касса (POS)
- Кассир сканирует штрихкод камерой телефона (или сканером/вручную) → система находит товар и текущую цену
- Формирование чека: список товаров, сумма, скидки/акции применяются автоматически
- Приём оплаты — наличные + карта через токенизацию платёжного провайдера
- Отмена/возврат позиции — с аудит-логом (кто, когда, что отменил)
- Офлайн-режим: очередь синхронизации при восстановлении связи (eventual consistency для склада) — **требует явного сценария разрешения конфликтов** (два кассира продают последнюю единицу товара одновременно без связи — кто побеждает, как не уйти в отрицательный остаток)

### Склад / инвентаризация
- **Приёмка сканированием с телефона** — навёл камеру на штрихкод, указал количество, товар оприходован; это основной сценарий приёмки, а не запасной
- **Остаток считается автоматически**: `текущий_остаток = начальный_остаток + приход − продано − списано`
- Каждая продажа списывает товар со склада в той же DB-транзакции, что и сама продажа
- Списания (порча, истёкший срок) — отдельная операция с указанием причины
- Алерт при низком остатке
- История прихода/расхода (аудит-лог складских операций)

### Отчётность
- Продано за день/период (количество и выручка)
- Остаток на складе в реальном времени
- Выручка и прибыль (нужна отдельная `CostPrice` — закупочная цена, отличная от продажной)
- Экспорт отчётов (CSV/PDF)

### Защита от злоупотреблений
- Себестоимость (`CostPrice`) — не видна кассиру и не видна другим StorePartner, отдельная авторизационная проверка на уровне use-case
- Аудит-лог фиксирует действия постфактум, но не предотвращает мошенничество кассира (пробить меньше, чем продано) — рассмотреть периодическую сверку остатка с фактическим, алерты на аномальные паттерны отмен/скидок

## 5. Доменная модель (Domain layer)

- `Product` — товар (штрихкод/EAN, название, категория, бренд, страна производства)
- `Store` — магазин (геолокация, владелец = StorePartner)
- `PriceEntry` — цена товара в конкретном магазине, с историей (для графика динамики)
- `Scan` — факт сканирования юзером (для топ-продаж и аналитики спроса)
- `Receipt` — чек, загруженный юзером, для сверки с ценником
- `Review` / `Report` — отзыв или репорт (неверная цена, нет в наличии, расхождение с чеком)
- `ContributorTrustScore` — репутация юзера-контрибьютора
- `ExpiringOffer` — товар с истекающим сроком со скидкой
- `ShoppingList` — список покупок юзера
- `SaleTransaction` — продажа (чек): дата, магазин, кассир, статус, сумма, способ оплаты
- `SaleLineItem` — позиция в чеке: товар, количество, цена на момент продажи
- `StockLevel` — текущий остаток товара в конкретном магазине (производная величина)
- `StockMovement` — запись прихода/списания/продажи (аудит-лог, из чего считается `StockLevel`)
- `CostPrice` — закупочная себестоимость товара (доступ строго ограничен)
- `Payment` — факт оплаты, привязан к `SaleTransaction`, хранит только токен от платёжного провайдера

## 6. Use-case'ы (Application layer)

Каждый Command/Query — со своим FluentValidation-валидатором, каждый обработчик реализует единственный интерфейс (ISP), зависит от абстракций репозиториев (DIP), без побочной логики вне своей ответственности (SRP).

**Консьюмерская часть:**
- `ScanBarcodeQuery` — распознать товар, вернуть цены по ближайшим магазинам
- `SubmitPriceUpdateCommand` — юзер обновляет цену (с валидацией и весом по репутации)
- `CompareStoresForShoppingListQuery` — "собери корзину дешевле"
- `VerifyReceiptCommand` — сверка чека с ценником
- `ReportOutOfStockCommand`
- `GetTopSellingProductsQuery`

**StorePartner:**
- `PublishExpiringOfferCommand`
- `GetStoreDashboardQuery`
- `ProcessSaleCommand` — провести продажу (атомарно: `SaleTransaction` + списание `StockLevel` + `StockMovement`), идемпотентный (защита от повторной отправки)
- `VoidSaleCommand` — отмена/возврат, с обязательной причиной и аудит-логом
- `RecordStockReceiptCommand` — оприходовать поставку
- `GetDailySalesReportQuery` / `GetProfitReportQuery` — доступ с проверкой владения магазином на уровне use-case
- `GetStockLevelQuery`

**Admin:**
- `ModerateNewProductCommand` / `ModerateReportCommand`

## 7. Роли (backend-логика авторизации)

- **User** — публичные эндпоинты сравнения/сканирования + защищённые (личный кабинет, список покупок)
- **StorePartner** — доступ только к своим `Store`/`SaleTransaction`/`StockLevel`/`CostPrice`, проверка владения на уровне use-case, не только по роли. Рассмотреть суб-роль "кассир" с урезанным доступом (без себестоимости/финансовых отчётов)
- **Admin** — модерация, полный доступ к аналитике платформы

## 8. Приоритизация backend-разработки

Приоритет считается от того, **за что магазин платит деньги**, а не от того, что интереснее покупателю.

**Сделано** (детали — в `WORKLOG.md`):
- Кабинет магазина: касса (`ProcessSaleCommand`/`VoidSaleCommand`/возвраты), склад, смены кассира, поставщики и закупки, акции, лояльность, GiftCard/StoreCredit, отчёты по продажам и прибыли
- Каталог и справочники (Product/Category/Brand/TaxRate/Supplier) с полным CRUD
- Identity + JWT, роли, суб-роль кассира, refresh-токен, rate limiting, CORS, HSTS
- Потребительская часть: скан, сравнение корзины, краудсорс цен, сверка чека, жалобы
- Admin-консоль модерации

**Следующее по значимости (не сделано):**
1. **Бухгалтерский учёт** — расходы/доходы магазина, взаиморасчёты с поставщиками и покупателями (долги), учёт по кассе и банку. Без этого Sarfkor остаётся кассой, а myfin.tj — системой учёта; это главный функциональный разрыв с конкурентом
2. **Фискализация чеков** — см. §9, блокер юридический, а не технический
3. Офлайн-режим кассы и разрешение конфликтов синхронизации
4. Экспорт отчётов (CSV/PDF) — базовое ожидание бухгалтера магазина
5. Нагрузочное тестирование и мониторинг (§10)

**Сознательно отложено:**
- B2C-фичи, не приводящие магазины: расширенная аналитика спроса для покупателей, бенчмаркинг конкурентов

## 9. Открытые вопросы (backend)

- **Глубина бухгалтерского учёта** — где граница между «учёт для владельца магазина» и полноценной бухгалтерией для налоговой? myfin.tj закрывает второе. Минимум, который нужно решить: ведём ли мы взаиморасчёты (долги поставщикам и от покупателей), расходы магазина (аренда, зарплата, коммуналка) и движение по кассе/банку — или ограничиваемся выручкой и прибылью от товара, как сейчас
- Источник базы товаров по штрихкодам: собственная с нуля vs интеграция с открытой базой (Open Food Facts и аналоги) — **блокер №1, решить до начала разработки**
- Разрешение конфликта при одновременных разных репортах цены + защита от сговора против рейтинга магазина
- Выбор платёжного провайдера/эквайринга для Таджикистана
- ~~Нужна ли суб-роль "кассир"~~ — **решено:** да, реализована через `StoreEmployee` + `StoreEmployeeRole { Owner, Cashier }`
- **Фискализация чеков**: требования налоговой Таджикистана к POS — потенциальный юридический блокер
- Юридические требования к персональным данным (чеки, геолокация, платежи) в Таджикистане

## 10. Критические замечания — закрыть перед реальным запуском

### Конкурентоспособность против myfin.tj (главное)
- **Нет бухгалтерского учёта** — есть выручка и прибыль от товара, но нет расходов магазина, взаиморасчётов с поставщиками и покупателями, движения по кассе/банку. Для владельца магазина, который сравнивает нас с myfin.tj, это первый вопрос, на который у нас нет ответа
- **Фискализация чеков не реализована** (`FiscalReceipt` сознательно пустая, см. §9) — без ответа налоговой любой магазин, обязанный выдавать фискальный чек, физически не может перейти на нашу кассу. Это блокер продаж, а не «доработка на потом»
- Нет экспорта отчётов в CSV/PDF — бухгалтер магазина ожидает выгрузку по умолчанию

### Архитектура и надёжность
- **Нагрузочное тестирование не проводилось** — проверить производительность запросов сравнения цен на реалистичном объёме (сотни магазинов, десятки тысяч товаров), EXPLAIN ANALYZE, продумать индексы
- **Офлайн-режим кассы вообще не реализован** — ни очереди синхронизации, ни сценария разрешения конфликтов. Для магазина с нестабильным интернетом это блокирующее ограничение
- **Нет плана миграции схемы БД без даунтайма** для уже подключённых магазинов
- **Нет мониторинга/алертинга** — есть только `GET /health`, дашборда состояния системы (Grafana/аналог) нет
- ~~Нет тестового покрытия Domain-слоя~~ — **закрыто:** 259 тестов, включая все три инварианта кассы (идемпотентность, двойной void, отрицательный остаток) + интеграционный тест конкурентного списания против реальной PostgreSQL
- ~~Rate limiting без конкретных цифр~~ — **закрыто:** 6 именованных политик с конкретными лимитами (§2)

### Защита от злоупотреблений
- Защита от мошенничества кассира — реализована только эвристика `GetCashierAnomalyReportQuery` (аномальные паттерны отмен). Периодической сверки фактического остатка с учётным по-прежнему нет

### Операционное
- Модель поддержки не определена — команда из 2 человек не потянет 24/7 при масштабировании
- Юридическая проверка фискализации и персональных данных не проведена
